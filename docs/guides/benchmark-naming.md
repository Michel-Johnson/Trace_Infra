# 集合命名规则

## 三个概念分开

| 字段 | 规则 | 示例 |
|---|---|---|
| 显示名称 title | 领域/对象 + 能力/任务 + 分析集；可以使用中文 | 多维表格搭建分析集 |
| 稳定身份 id | 小写英文、数字、短横线；建议 domain-capability，3–64 字符 | bitable-build |
| 发布版本 revision | 独立记录；题目或约束变化形成新版本 | 1.0、1.1、2.0 |

任务集使用相同规则，名称末尾可用“任务集”。Case 的 query_id 独立命名，例如 supermarket-ledger，不把 query 全文或标题当作 ID。

建议示例：文档编辑分析集 doc-edit、代码修复分析集 code-repair、多轮任务执行分析集 agent-multiturn。范围是稳定定义的一部分时可以加入 ID，例如 bitable-build-zh。

不建议用 test、final、new、我的分析集 等无法长期辨认的名称；不在分析集 ID 中加入被比较的模型、harness、沙箱或一次运行日期。这些放在 Run/环境/实验元数据中。若分析任务本身研究某个时间窗口或固定环境，则可在任务描述和约束中明确。

规则是新建时的推荐规范，不批量重命名已有集合，不改变旧 query_id 或链接。显示名称不是身份，跨集合复用相同 Case 时沿用 query_id。

## 当前服务的版本边界

线上 catalog/1.0 暂无独立 revision 字段，首页表单不会假装保存版本。当前每个集合 ID 对应一份不可覆盖的清单；题目清单变化时使用新 ID，例如 bitable-build-v2，并说明与原集合的关系。下一版平台协议将 family id 与 revision 分开，已有 ID 保持可追溯。

新建入口用于从已有 Case 组建集合；新 Case 可通过“导入轨迹或集合清单”进入平台。名称、ID、类型和题目选择直接写入现有集合协议，评分及运行数据不属于命名或创建动作。
