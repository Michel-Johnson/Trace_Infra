# 版本管理规范

本规范适用于自本文件首次进入 `dev` 起的每一个新提交（包括文档、测试、修复和合并提交）。历史提交不补号、不重写。`dev` 是开发集成分支；未经用户明确要求，不将其自动合入 `main`。

## 两类版本

- **开发提交版本**：标识 `dev` 上的一个确定 Git 提交，格式为 `vMAJOR.MINOR.PATCH-dev.N`。`N` 是当前目标发布版本下从 1 开始、逐次加 1 的整数。每个进入 `dev` 的新提交必须有且只有一个独一无二的开发提交版本。
- **产品发布版本**：格式为 `vMAJOR.MINOR.PATCH`，只在确定发布范围并完成验收后使用。破坏兼容性升 `MAJOR`，向后兼容的新功能升 `MINOR`，向后兼容的修复升 `PATCH`。`0.x` 阶段也按此约定记录变更，但不承诺稳定 API。

前端 `package.json`、页面展示的是**已发布的前端产品版本**，不是每个开发提交的编号。OpenAPI、Skill 和插件可以有各自的合同/包版本，不得拿这些版本替代仓库开发提交版本。

## 每次提交到 `dev` 的要求

1. 从最新 `origin/dev` 确定下一个开发提交版本。当前线上前端为 `0.3.0`，本规范提交从 `v0.3.1-dev.1` 开始；同一目标版本的后续提交依次为 `v0.3.1-dev.2`、`v0.3.1-dev.3`。若经评估下一次发布应为 `0.4.0`，则从 `v0.4.0-dev.1` 开始，之后不得回退到较低的目标版本。
2. 提交标题以 `[vMAJOR.MINOR.PATCH-dev.N]` 开头，提交正文末尾保留同值的 `Dev-Version:` trailer。例如：

   ```text
   [v0.3.1-dev.2] fix(web): restore trace search layout

   Dev-Version: v0.3.1-dev.2
   ```

3. 一次推送包含多个提交时，**每个提交**都要分别编号；不能只给分支最后一个提交编号。合并前优先 rebase 或 squash，确保最终进入 `dev` 的每个提交满足本规范。若使用合并提交，它也须有自己的下一编号。
4. 只允许快进推送 `dev`，不得强推。若别人先推送了新提交，先更新 `origin/dev`，再为自己的提交重新编号并核对标题与 trailer；重复编号或跳号不得推送。版本号一经进入 `dev`，不得复用。
5. 未提交的工作区、构建目录和服务器文件不构成版本。单纯重新部署同一提交不产生新的开发提交版本；部署记录仍须指出原提交和该版本。

## 发布与回退

- 发布前确定产品版本和范围，核对源码提交、依赖锁、测试结果、前端显示、API/Skill 合同以及构建产物。发布记录至少包含产品版本、开发提交版本、完整提交 SHA、构建产物哈希、部署时间、上一个发布目录和回退入口；当前服务器的实际发布状态仍以私有 `platform-release.json` 为准。
- 正式 Git Tag 使用 `vMAJOR.MINOR.PATCH`，仅指向已验收的确定提交；开发提交不逐个打 Tag。是否合入 `main`、何时打正式 Tag，遵守用户对 `main` 的明确授权要求。
- 代码回退不得覆盖更新的持久化数据。紧急线上静态修复也要补对应的 `dev` 带版本提交，并记录所基于的原发布产物，避免下一次构建恢复旧文件。

## 推送前检查

```bash
git fetch origin dev
git log --format='%h %s%n%b' origin/dev..HEAD
git log -1 --format='%B' origin/dev
git diff --check
```

逐条核对待推送提交的标题和 `Dev-Version:` 一致，且版本相对于远端最新提交连续递增。发布时再核对 `package.json`、锁文件、界面版本和发布记录。本文是提交规范；仓库目前尚无自动拒绝缺号/重号提交的 CI 规则，不能把人工检查称为自动保障。
