Trace 是记录。
评价取决于你想知道什么。

一次工具调用失败后，Agent 换了一种方法完成任务。效率团队会关注多花的时间，可靠性团队会关注它如何恢复，业务团队会核对最后的产物。三种看法都应能引用同一份记录。

平台保存可追溯的事实，插件表达业务理解。 不把某种业务的“好轨迹”定义写死在采集和存储里。

中性不等于没有结构。消息、模型请求、工具执行、时间、原始返回和缺失声明需要明确记录；“属于什么业务阶段”“是否符合要求”则需要说明评价者、规则和证据。

不变的抽象

换一种业务，核心仍然成立。

能力负责什么本次范围
记录与版本保留身份、原文、来源；补采形成新版本已有后端实现
存储与恢复正文与元数据分开，旧引用可回读PostgreSQL + 持久内容目录
搜索与切片按条件定位、分页，固定要处理的成员有界查询与冻结选集
回放固定输入和环境条件，新执行产生新轨迹通用回放与独立验证待交付
存储分片大正文分块，保持清单、摘要和重组关系待容量验证后实施

“分片”不要混成一件事

只看第 2 轮是逻辑切片；把大正文拆成可恢复的块是存储分片；把样本组织成训练文件是训练分片。当前已有分页和固定选集，后两项仍在路线图中。

回看历史，也不等于重新执行

网页回看已有消息；重新分析使用新的规则；真正回放会使用录制结果、重执行动作，或重新调用模型。它们需要不同的条件和验收方式。现有远程执行接口为回放提供基础，尚未交付环境恢复和通用回放。

接入前，先问服务支持什么

稳定网页导入使用 1.0 / 1.1。新版版本接口还支持实验性的 v2-storage-1。采集侧继续演进的 v2 草案不自动进入生产：客户端应同时核对 profile 与 Schema 摘要，不能只看版本名称。

可变的业务理解

一个业务插件，可以有多种能力。

“Base 生成”是业务用途。它可以同时提供阶段分类、耗时统计和专属视图。renderer、分类器、评分器是实现方式，并不是插件必须互斥的类别。

同一份数据各自的解释
执行状态：errorBase 插件：base.stage = permission
记录与用户轮次关联归因复核：这个要求是在下一轮才提出的
相邻两次请求与返回可靠性插件：观察到一次有效恢复

简单备注可以作为自定义属性；可重复的分析应由插件完成。业务属性带命名空间、目标版本、产生者、规则版本和证据。来源自带的标签保留为来源声明，多个插件的意见可以共存。

现有结构化产物和任务接口可用于接入；统一的任意自定义属性写入、索引与权限合同仍需继续收敛。

Roadmap / 按成果验收

先把现有能力接成一个平台。

本次交付

平台核心与使用说明上线

发布已验证的 Python 核心，补齐持久内容目录、执行 Worker、固定协议发现与文档入口。保留现有数据和登录，记录发布版本与检查结果。

下一步

业务属性和产物贯通

让现有业务分析通过正式插件接口保存，网页与 Agent 读到相同的结论和证据；统一自定义属性、插件组合和采集兼容范围。

后续

真正回放，独立验证

先支持一个可恢复环境，再逐种交付回放方式。重跑生成新轨迹，独立检查产物，环境失败与模型失败分别记录。

后续

训练出口与规模扩展

固定样本、转换规则、训练分片和消费回执。根据实际数据量与性能瓶颈再决定对象存储、物理分片、分析读库或 Rust。
