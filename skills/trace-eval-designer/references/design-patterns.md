# Trace Eval 设计模式

先按问题类型选择设计，再读取对应部分。模式是起点，不是预设答案；字段和接口必须以当前 Trace 数据与服务能力为准。

## 1. Skill 加载成本

**问题**：加载某个 Skill 是否消耗异常耗时或 Token？

- 单位：一次明确的 Skill load/invocation Span。
- 证据：Skill 名称与 revision、开始/结束时间或 duration、输入/输出 Token、模型、环境、任务标识。
- 指标：P50/P95/P99、均值、长尾比例、Token 分布、缺失覆盖率。
- 分组：Skill revision、模型、环境和任务类型。
- 风险：总 Trace 耗时不能直接归因给 Skill；Skill 自身和子工具时间需声明是否去重。

## 2. 有 Skill / 无 Skill 的效果比较

**问题**：面对同类任务，读取 Skill 是否与更好的结果相关？

- 单位：同一 query/task 的运行，或匹配后的运行对。
- 暴露变量：是否读取指定 Skill，并固定 Skill revision。
- 结果变量：独立任务结果、成功率、错误率、耗时、Token 或步骤数量。
- 必须匹配：任务、模型、Harness、环境、工具权限和时间范围。
- 输出：两组样本数、覆盖率、差异和剩余混杂因素。

历史 Cohort 只能支持观察性结论。若要回答因果问题，设计受控实验：相同任务和环境随机分配 Skill 条件，隔离每次运行，并使用同一独立 Verifier。只有此时才考虑 Harbor 等实验运行层。

## 3. Skill 指令遵循

**问题**：Agent 读取 Skill 后是否遵守其中与当前任务相关的要求？

- 单位：Skill 可见后的决策点或行为链。
- 证据：Agent 实际看到的 Skill 版本、当时用户目标、`model_context`、后续工具调用及结果。
- 方法：代码固定 Skill、时间窗口和行为候选；LLM Judge 仅判断明确列出的指令与行为是否一致。
- 判定：`compliant / non_compliant / not_applicable / unknown`，不要把不适用当作通过。
- 风险：用最新版 Skill 替代实际 revision，或用后续报错反推模型先前应该知道，都会造成信息穿越。

## 4. 工具调用合理性

**问题**：某次 Tool Call 是否为完成用户任务所需，参数和调用时机是否合理？

- 单位：单次 Tool execution，而不是文本中的 proposal。
- 证据：用户目标、此前可见上下文、工具名和参数、结果、后续修复行为。
- 方法：代码检查硬规则；语义必要性由受限 Judge 判断。
- 分开评价：是否必要、工具是否合适、参数是否安全、结果是否被正确处理。
- 风险：失败的调用不一定不必要，成功的调用也不一定合理。

## 5. 重复调用与错误模式

**问题**：工具是否重复调用并出现相同或相关错误？

- 单位：Tool attempt 或来源明确的 retry chain。
- 证据：call/request/attempt 身份、规范化工具名、参数摘要、错误类型与正文、顺序和关系。
- 方法：先按结构化错误状态筛选，再对错误正文做 literal/regex 召回和签名归一化。
- 指标：错误率、重复次数、无参数变化重试率、恢复率、受影响 Trace 数。
- 风险：没有 attempt/retry 证据时，只能称为相似的后续调用，不能断言重试。

## 6. 行为链和漏斗

**问题**：A 发生后是否依次发生 B、C，在哪一步中断？

- 单位：同一 Trace 内满足身份、方向和时间约束的行为链。
- 证据：Span 关系、来源顺序、时间和对象类型。
- 方法：评测器根据固定样本的对象证据计算每一步到达率，并保留中断样本。
- 风险：文本同时出现 A/B/C 不代表行为链；跨 Trace 命中不能拼成一次执行。

## 7. 数据完整性

**问题**：Trace 是否缺少评测所需信息？

- 单位：Trace revision 或需要字段的对象。
- 指标：Span、关系、正文、状态、耗时、Token、Context 和来源引用覆盖率。
- 判定：区分来源本来未提供、Adapter 丢失、索引未完成和权限不可见。
- 风险：数据缺失是平台/采集事实，不应直接计为 Agent 质量失败。

## 8. 探索性异常发现

**问题**：一批 Trace 中是否存在共同错误或异常特征？

- 先把它定义为假设发现，不直接输出稳定评分。
- 使用结构化分组、错误签名、分布长尾和代表样本产生候选模式。
- 每个候选模式记录支持样本、反例、覆盖率和可能混杂因素。
- 经人工复核后，用本 Skill 将候选模式转换成独立 Eval Spec，再进入全量验证。

## 组合原则

一个用户目标可以产生多个 Spec。例如“Skill 是否有效”通常至少拆为加载成本、任务结果、行为合规和副作用四项。分别输出指标和证据，最后再由报告层综合，不提前压成一个难以解释的总分。
