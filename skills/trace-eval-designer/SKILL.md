# Trace Eval Designer

## 版本预检

版本页：[查看最新 Skill](http://10.37.24.3:8766/skills.html)；机器接口：[查询版本](http://10.37.24.3:8766/api/skills/manifest)；[下载官方包](http://10.37.24.3:8766/api/skills/archive)。仅在服务器的 tracehunter-agent 隔离 worker 中，若公网入口连接拒绝或超时，改用 [worker 版本接口](http://127.0.0.1:8767/api/skills/manifest) 和 [worker 下载接口](http://127.0.0.1:8767/api/skills/archive)；HTTP 错误不能靠切换地址绕过。

每次使用前确认接口返回 HTTP 200 且有本 Skill 的版本条目，下载同一入口的官方包并逐文件对比本 Skill。空输出、非零退出码或无法读取压缩包都不是通过；记录检查结果。安装态有更新时保留用户改动并更新、校验；仓库开发态只报告差异，不用线上包覆盖源码。无法检查或更新时停止。

把用户想研究的问题变成 Trace Hunter 能执行、评审者能复核的 Eval Spec。先理解决策目标，再设计指标和查询；不要从现有字段反推用户只能评测什么。

设计和评审 Eval Spec 是持续对话，不因进入本 Skill 或产出 Draft/Approved Spec 就创建工作台任务。用户随后要求按已批准的 Spec 开始评测时，把 Spec 身份、总体、规则、阶段和完成条件交给 Batch Analyzer；在实际执行前询问是否创建评测任务。得到肯定答复后才由执行流程创建任务，设计阶段不要抢先创建。

## 工作方式

1. 阅读用户提供的需求、样例 Trace、既有评测和当前平台能力。能从资料确认的事实不要反问用户。
2. 判断问题属于描述统计、异常诊断、行为合规、观察性对比还是受控实验。问题类型的选择方法见[设计模式](references/design-patterns.md)。
3. 只追问会改变评测结论的事项：评测对象、分析单位、适用范围、成功定义、对照条件、可接受的未知项和最终用途。
4. 明确所需证据及可见性边界，再决定确定性规则、统计方法、LLM Judge 或混合方法。不得先选择 Judge 再寻找任务。
5. 检查 Trace Hunter 当前能力，给出具体查询计划和能力缺口。涉及 CLI/API 时读取[Infra 查询规划](references/infra-planning.md)。
6. 按[Eval Spec](references/eval-spec.md)输出 `Status: Draft` 的完整草案，标出假设和待决项；与用户评审后才能改为 `Approved`。

## 核心不变量

- **不信息穿越**：判断 Agent 当时是否应采取某动作，只能使用当时对 Agent 可见的内容。事后诊断数据必须与 `model_context` 证据分开。
- **不补造事实**：缺失耗时、Token、关系、结果或上下文时返回 `unknown` / `insufficient_data`，不得当作 0、未发生或失败。
- **身份稳定**：以 `(project_id, run_id, revision, span_id)` 等稳定身份连接证据，不按标题、数组位置或相似文本拼接。
- **观察与因果分离**：历史 Trace 的有/无 Skill Cohort 通常只能说明相关性。要证明因果，需要匹配混杂因素或设计同任务、同环境的受控重跑。
- **评分独立**：不要用被评测 Agent 的自述作为唯一真值。优先采用环境结果、结构化状态、固定输入和独立证据。
- **版本固定**：固定 Trace revision、Skill revision、模板版本、模型与环境范围。`latest` 只适合探索，不适合作为不可复现的最终评测定义。
- **查询不等于结论**：Trigram 是正文索引实现，公开搜索模式只有 literal 与 regex；候选命中仍需结构、关系、时序和必要正文证据复核。
- **样本不等于总体**：局部 Trace 只能支持局部描述。写“全部”“始终”或总体比例前，固定总体与分层（如 env_id/harness），完整分页、报告分母/覆盖率，并查找反例；做不到时限定为已观察样本。
- **重试须有任务关联证据**：同名、同参数或较晚调用只构成 `retry_candidate`。无 `retry_of`、同任务上下文或明确调用链证据时，重试与“不重试是否有风险”均保留 unknown，不能自动判确定风险。

## 方法选择

- 能由字段、关系、时间或精确文本确定的条件，使用代码规则。
- 需要比较分布、比例或 Cohort 的问题，使用统计方法并报告分母、覆盖率和置信边界。
- 需要理解用户意图、Skill 语义或行为合理性的条件，才使用 LLM Judge；先用代码固定候选范围和可见 Context。
- 混合方法中，代码负责取证和硬约束，Judge 只判断明确列出的语义维度。Judge 无法看到必要证据时必须返回 `unknown`。

## 交付要求

每次设计至少交付：评测问题、分析单位、数据范围、证据契约、指标或判定规则、查询计划、未知语义、校准案例、能力缺口和版本信息。复杂任务可以拆成多个独立 Eval Spec，不要用一个总分掩盖不同问题。
交付前逐条对照 `verdict.rules`、`known_gaps`、`assumptions` 和 `open_decisions`：已承认无法区分的情形不能在判定规则里当作确定事实；待决阈值不得伪装成已批准标准。

只设计评测时不要运行全量分析、注册插件或创建 Harbor Task。用户明确要求继续执行时，再交给 Trace Hunter CLI、批量分析器或受控实验运行层。
