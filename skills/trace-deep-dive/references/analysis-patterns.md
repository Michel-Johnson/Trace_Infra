# 四方面检查

依据上游 Eval Spec，每方面给出 `符合`、`存在问题`、`无法判断` 或 `不适用`，并说明所依据的事实；Draft Spec 下只是暂定个案判断，不是正式分数。只有当前目标确实不涉及该方面，才用“不适用”；需要证据却没有证据时用“无法判断”。同一事件可影响多个方面，但只能把有证据的后果写进对应方面。

## 结果质量

从用户目标或 Case 验收条件拆出检查点，核对最终产物、环境状态或独立验收结果。`completed`、提交动作和 Agent 自称成功都不等于任务通过；只有错误 Span 也不等于整个任务失败。没有验收器或产物无法读取时，只描述可见结果，不推断最终可用性。

## 执行过程

沿来源顺序重建关键决策、执行与反馈，找首次可证实的遗漏、偏离、循环或错误恢复。固定 Agent 实际读取的 Skill 版本，把相关条款和用户约束映射到要求可见之后的行为；没有结构化 Skill 记录时，不能用当前 SKILL.md 反推当时已读取。`source_ordinal` 证明记录顺序，不单独证明因果；有并行或截断时标明范围。

## 工具调用

分开核对工具是否适用于任务、当时是否可用、提议参数是否正确、是否真实执行、返回/报错是否被处理。文本提及不是调用，proposal 不是执行；调用失败不自动说明选错工具，调用成功不自动说明选对工具。若原始输出显示工具迹象而结构化 Tool Span 缺失，记录为取证缺口，不判“没有调用”。

## 效率与稳定性

只报告采集到的时长、Token、调用次数与错误/恢复链，并注明单位和缺失范围。相似调用只有显式 `retry_of` 或同任务上下文等证据才称为重试，否则称“后续相似调用”；区分参数修正与无变化重复。没有任务/环境可比基线时，不把高耗时或高 Token 直接判成浪费；没有后续终态时，不宣称已恢复。

## 归因与数据边界

问题需同时指出首次偏差和受影响结果；分别考虑 Agent 决策、工具/环境限制、用户信息不足、Skill 冲突和 Adapter/索引记录问题。来源未提供、Adapter 丢失、投影缺失、索引未完成、权限不可见要单列，不计作 Agent 失败。对无法排除的解释保留 `hypothesis`，并写明什么证据可以推翻它。
